## 2. 必须达成的画面与体验

Alpha 的主画面来自《创造亚当》的双手构图：人类手从左上伸出，粒子手从右下伸出，指尖接近但不接触。画面有古典比例、安静的留白和清楚的立体感。

### 主画面

1. 左手为真实三维形状，使用柔和、偏石膏或浅色雕塑的实体材质。主要立体感来自正确解剖、轮廓、明暗和遮挡。
2. 几何构造线对应腕关节、指节轴线、掌骨方向、比例关系与实际轮廓。线的存在应有结构理由。
3. 右手由三维粒子形成，手指、指缝、手背和手腕都能辨认，沿右下方向逐渐疏散。
4. 右手具有轻微周期漂移或呼吸。鼠标接近时只扰动邻近粒子，鼠标离开后恢复手形。
5. 主画面空闲时相机稳定。大幅旋转、自由漫游和持续镜头摇摆不属于本版体验。
6. 主画面中只有双手、对应构造线和克制的导航提示。输入框只属于左上目的地。
7. 主手必须是可参与形态转换的三维素材。原始参考图用于对齐与检验，不能将整张参考图作为最终画面的背景来代替实现。

### 严格参考图匹配

用户明确要求：手指弯曲、手腕角度和轮廓都尽量一比一贴合几何版本。先匹配主镜头下的投影，再发展动画。

至少对齐：双方食指指尖位置、指尖间距、手腕进入画面的位置与角度、各指弯曲与遮挡、手掌外轮廓、两手占画面的比例，以及中央留白。

“匹配”针对指定主视角。参考图没有展示的侧面需要合理补全。最终材质按雕塑方向制作，因此无需复刻参考图每个像素的灰度与笔触。

在 1644 × 957 的检查画幅上保存参考叠加图、关键点或轮廓对比。先给出可以复查的对齐证据，再宣称达到高贴合。放大截图检查指节、指缝与手腕，不能只检查缩略图。

### 启动

先预加载必要模型、纹理与粒子数据。资源就绪后：

- 两只手分别从左上和右下方向缓慢进入最终构图，手腕沿画面边缘延伸，避免露出突兀的截断面。
- 左手的定位线、构造线和轮廓逐步描出，随后立体表面显现。
- 右手的悬浮粒子收拢到手形。
- 两侧动画共享一个可调时间轴；初始时长建议约 2.8 秒，属于可调整参数。
- 启动及主画面中，大脑、科技树、输入框都完全隐藏；隐藏元素也不得接收点击、Tab 焦点或 hover。
- 主画面稳定后才开启导航热区。

背景暂以参考图的浅暖白为起点，粒子和细线使用炭黑或灰色。分隔轴通过构图表达；为贴合几何参考图，v1 默认不额外增加贯穿全屏的明显 divide line。将此作为工程默认值记录，保留以后调整的余地。

## 3. 空间导航与变形关系

使用同一个持续存在的场景。左上、主画面、右下是同一连续空间中的三个观察位置，不触发文档刷新。

| 所在位置 | 左上角 hover | 右下角 hover |
|---|---|---|
| 主画面 | 前往左上区域 | 前往右下区域 |
| 左上区域 | 无新导航 | 返回主画面 |
| 右下区域 | 返回主画面 | 无新导航 |

这里的“角落”指**应用内容区域**的角落，鼠标坐标来自应用内部，不依赖桌面全局鼠标位置。

### 前往左上

- 相机沿左上方向移动，并以平滑的加减速进入目的地。
- 左手承担主转换：雕塑实体显露构造线，构造线与采样粒子解体、迁移，重新组织成粒子大脑。
- 右手是辅助元素，可以散开到边缘成为氛围粒子。
- 接近目的地时，大脑完整形态与输入框逐步出现；到达后相机停住，输入框可以正常使用。

### 前往右下

- 相机沿右下方向移动。
- 右手承担主转换：粒子离开手形，逐渐组织为科技树的节点结构，连接线随后显现。
- 左手是辅助元素，可以沿构造线解体，进入边缘的轻量线段或粒子氛围。
- 右下区域显示科技树及简单节点信息，不出现第二个自然语言输入框。

### 边框氛围粒子的明确处理

用户将这一效果标为“暂定，假设没有效果”。本任务采用以下可回退的解释：

```ts
ambientBorderParticles: false
```

- 默认关闭，**不是 v1.0.0 必须完成的效果**。
- 关闭时，辅助侧的手随转场解体、散出视野并淡隐，目的地边缘没有持续氛围粒子；主转换照常完成。
- 保留辅助侧的原始位置、粒子 ID 和重组路径，以便返回。
- 核心体验完成且性能有余量后，才可增加此效果作为可选配置；开启与关闭都不能改变导航状态或主变形路径。

### 返回

反方向角落触发返回，目标区域的结构沿相反过程重组为主手，辅助侧同步恢复。左侧返回应能看见大脑重新组织为左手，右侧返回应能看见科技树重新组织为右手。

每次回到主画面时，双手姿势、粒子分布基准、指尖间距、相机位置和构造线保持一致。启动动画与返回动画是不同流程，返回不得简单重播开屏来掩盖缺失的逆向变形。

## 6. 手部素材制作流程

### 6.1 先解决造型

1. 检查现有素材与 Blender 是否可用。
2. 优先寻找许可清楚、可用于本项目的三维基础手模型，再调整成左右两侧需要的姿势。记录来源、许可和改动。
3. 在 Blender 中固定主镜头投影、画幅与参考图；按手指、手腕、轮廓逐项调整。两侧姿态分别校准，正确处理拇指位置和左右手关系。
4. 设置柔和雕塑明暗，让手指、指缝、掌骨与手腕有可辨认体积。
5. 主视角通过对齐检查后，再建立几何构造线与粒子目标。

基础模型、手工调整和离线脚本都是可接受的制作方式。不要把普通圆柱拼接手当作最终资产，也不要用全屏后处理掩盖手形不准。

如果暂时只能获得占位模型，仍可继续完成场景和交互，但必须将造型差距列为未完成事项，不能将占位模型宣布为已通过的 v1.0.0 成品。购买素材需要用户明确授权；先完成可用素材的实际筛选与差距说明。

### 6.2 几何构造线

构造线至少包括适量的腕部截面／圆弧、指节定位、比例关系和轮廓曲线。根据解剖标志制作路径，让启动时的描绘具有可理解的顺序。

将线条路径及其绘制顺序保存为可重现数据。曲线在三维空间或受控的投影层中与手形对齐，随转场一起移动。线条粗细尽量以屏幕像素控制，防止缩放后过粗或消失。

Blender 中的任意节点材质或曲线不会自动成为相同的实时效果。导出时使用受支持的几何／材质表达，必要时将构造路径单独导出，并在 Three.js 中实现描绘与解体。参考 [Blender glTF 导出说明](https://docs.blender.org/manual/en/latest/addons/import_export/scene_gltf2.html)。

### 6.3 粒子与可重复性

从已经校准的手部表面进行加权采样，保存稳定 seed、粒子 ID、原始位置和所需法线。适当加强轮廓、指尖和指缝附近的可读性，在腕部和尾部增加疏散。

可用 [MeshSurfaceSampler](https://threejs.org/docs/pages/MeshSurfaceSampler.html) 作为采样起点。最终视觉需检查团簇、空隙、大小差异与形体明暗，不能仅依赖均匀随机点。

## 7. 场景、相机和动画实现思路

### 7.1 单一世界坐标

定义 `HOME`、`HUMAN`、`SYSTEM` 三个世界空间锚点及其相机目标。左上和右下沿同一对角方向展开。主场景不因导航而卸载重建。

相机可先使用正交投影或较长焦距的透视投影；以参考匹配结果选择并记录。粒子大脑本身仍具有真实深度。主镜头、手模型姿态与材质一经校准，应作为可恢复的配置保存。

输入框、节点详情等使用 DOM；在转场期间与场景共享进度控制位置、透明度和交互状态，确保内容是沿空间运动被引出，而非末尾突然弹出。

### 7.2 状态机与唯一进度来源

建议的主状态：

```ts
type SceneState =
  | 'loading'
  | 'intro'
  | 'home'
  | 'toHuman'
  | 'human'
  | 'fromHuman'
  | 'toSystem'
  | 'system'
  | 'fromSystem';
```

每次转换只有一个主进度 `p ∈ [0, 1]`，相机、手部解体、粒子迁移、连接线和 DOM 显现都由这个进度计算。GSAP 驱动进度，帧循环应用结果。不要让多个动画控制器同时写同一相机属性。

进入时 `p: 0 → 1`，返回时沿同一路径 `p: 1 → 0`。保留需要逆向播放的几何和数据；不要在正向结束时销毁它们。

建议阶段如下，具体比例集中配置：

| 转场进度 | 视觉职责 |
|---|---|
| 0–20% | 相机开始移动，主手显露构造／粒子结构，辅助手开始散开 |
| 20–65% | 元素沿方向迁移，目标结构逐渐可辨认 |
| 65–90% | 大脑或科技树基本形成，目的地文字／输入框开始出现 |
| 90–100% | 相机减速停下，内容稳定，开启目的地交互 |

初始转场时长约 1.6 秒，属于调参起点。根据实际观感调整，不将数值当作已确认的美术要求。

### 7.3 变形数据

为对应粒子保存手形目标、目的地目标和少量路径控制点，所有坐标使用一致的空间约定。

概念上可写为：

```text
position(i, p) = path(handPosition[i], targetPosition[i], p)
              + envelope(p) × seededDisturbance(i, p)
```

`envelope(0) = envelope(1) = 0`，确保主画面和目的地端点不会因为扰动漂移。返回使用同一粒子映射与路径。需要完全可逆的扰动用 ID 和进度确定，不能重新随机生成。

手部空闲呼吸、鼠标扰动是另一层小幅变化；在变形边界处平滑收敛，避免进入或返回时跳变。

目标点映射尽量保留空间邻近关系，避免大量粒子无意义地交叉穿越。大点集的映射和布局在预处理或加载阶段计算；帧循环主要更新进度与少量参数。

左手通过“实体可见度／局部揭示 → 构造线 → 采样粒子”的重叠阶段过渡。右手沿已有粒子数据转换。科技树中多个视觉粒子可以分布在同一节点附近的小范围形状中，节点连线在布局趋于稳定后显现。

## 8. Hover 与输入处理

- 设置尺寸可配置的左上、右下热区，与相邻手腕的视觉方向对应。
- 初始 hover 停留阈值建议 350 ms；鼠标在阈值前离开则取消。
- 导航开始后执行完整的受控转场；途中忽略重复导航请求。
- 到达后需先离开触发热区，再允许新的 hover 触发，防止连续往返或误启动。
- 用当前状态决定角落的意义，严格遵守导航表。
- 热区提示应克制，避免主画面出现大按钮、菜单面板或调试文字。
- 粒子 hover 与导航 hover 独立：前者更新局部扰动，后者只由角落停留触发。
- 输入框获得焦点时正常接收文字；隐藏面板不保留焦点。提供 Escape 返回作为键盘补充，不能取代已确认的反方向 hover。
- 支持减少动态效果偏好，使用缩短、低幅度的过渡，保持相同的目的地与返回逻辑。

热区可使用透明 DOM 元素承载，以获得可靠的指针事件、可访问名称和自动化定位；画面仍由 Three.js 呈现。为测试设置稳定的 `data-testid`，不在产品界面展示测试 ID。

## 9. 针对目标机器的运行策略

目标环境：**Arch Linux、KDE Plasma、Wayland、16 GB RAM、Intel i9-13900H、Intel Xe 集成显卡，ASUS X1605VA**。

### 图形预算

- 以接近 1080p、DPR 1 的流畅 60 fps 为初始验证目标，不把硬件型号当作性能已经通过的证据。
- 初始可见粒子总预算可从约 12,000 起步，提供低／中质量配置，并根据实际帧时间调整。
- 粒子通过批量点云／实例绘制，在 shader 中计算漂移和局部鼠标影响。避免逐粒子创建独立 React 组件或 Mesh。
- 使用柔和灯光和适量预计算阴影细节，优先保证雕塑形体、构造线质量与转场连续性。
- 控制 drawing buffer 的实际像素数，处理 KDE 缩放和浏览器 DPR。质量变化不应改变构图。
- 页面隐藏或窗口最小化时暂停非必要动画；离开视野的对象停止无意义的更新。
- 稳定 seed 与预分配数组，减少帧循环中的临时对象及重复模型解析。

### Tauri 的实际验证

Tauri 的前端可沿用 Vite／React 结构，见 [前端配置](https://tauri.app/start/frontend/)。第一次可运行样机就加入桌面试跑，不把封装留到全部美术完成后。

Linux 版使用 WebKitGTK；官方记录了部分配置中的 WebGL／合成性能问题，见 [Linux Graphics Issues](https://tauri.app/develop/debug/linux-graphics/)。这不是对本机故障的判定，需要实测：

1. 相同场景分别在本机浏览器和 Tauri 中运行。
2. 记录图形相关运行信息、分辨率／DPR、加载后帧间隔、连续转场表现与输入延迟。
3. 检查 Wayland 下启动、缩放、调整窗口尺寸、最小化／恢复是否正常。
4. 不在没有复现问题时全局加入禁用硬件加速或 DMABUF 的环境变量。
5. 若 Tauri 的渲染问题持续妨碍核心体验，先证明同一场景在 Chromium 中表现正常，再用 Electron 外壳做有针对性的替代验证；保留前端代码，记录选择依据。Electron 已有原生 Wayland 支持，见 [官方说明](https://www.electronjs.org/blog/tech-talk-wayland)。

Playwright 的 Chromium 或 WebKit 测试结果均不能冒充 Tauri／WebKitGTK 实测结果。若运行环境无法启动桌面窗口，继续完成可验证部分，并把桌面验证明确列为未完成。

## 10. 推荐代码组织

可按实际项目调整，不必机械照搬：

```text
src/
  app/                 应用壳、版本与状态
  scene/
    AlphaScene.tsx     持续存在的三维场景
    HumanHand.tsx      雕塑表面与构造线
    ParticleHand.tsx   粒子手与鼠标扰动
    BrainView.tsx      粒子大脑
    TreeView.tsx       科技树
    CameraRig.tsx      唯一的相机控制入口
  transitions/        状态机、进度、往返路径
  particles/          数据、采样结果、shader
  ui/                 热区、输入框、节点详情
  config/             构图、时长、质量与可选效果
  fixtures/           共享的中性示例图数据
public/assets/        打包所需模型、点位、纹理与字体
assets-source/        可复现的模型或素材制作源文件
scripts/              采样、导出、对齐等必要脚本
src-tauri/            桌面外壳
tests/                少量关键流程回归
docs/                 视觉规格、实现决定、素材来源
outputs/qa/           截图、录制与验证报告
```

避免把素材下载、采样、相机、交互和全部 shader 都堆进一个组件。渲染层与桌面 API 分离，浏览器预览能独立启动。

## 11. 实施顺序

### 阶段 A：检查与最小运行环境

核对仓库状态和工具，读取图片；建立前端入口及最小桌面运行路径，确认目标系统具备所需依赖。若存在未提交工作，保留并在其基础上实现。

将本文关键需求整理进 `docs/VISUAL_V1.md`；将新旧需求冲突、可选氛围效果的解释和工程默认值记录到决策文档中，避免实施中重新猜测。

### 阶段 B：静态画面

校准相机和两只手的姿势，完成雕塑明暗、构造线、粒子密度与留白。保存主视角截图和参考叠加检查。造型未通过前，优先修正造型。

### 阶段 C：启动与空闲

完成角落移入、左手描绘、右手凝聚、低幅度周期运动及鼠标局部扰动。检查开屏期间没有目的地内容闪现。

### 阶段 D：先完成一条往返

优先实现 `home → human → home`，把相机、主手变形、辅助手退出、输入框出现及逆向重组真正连起来。验证状态与端点一致后，再实现 `home → system → home`。

### 阶段 E：性能与交付

在浏览器与可用的桌面环境中检查画面、交互与性能，修正实际问题。氛围边框效果在核心通过之后才评估，保持默认关闭。

完成启动说明、素材来源、截图／录制和验证结果。逐项说明已完成、未完成和环境限制。

## 12. Playwright CLI 与验收方法

### CLI 使用原则

用户明确允许 Playwright CLI。先查看当前安装版本和 `--help`，使用实际支持的命令；CLI 会变化，不猜测不存在的子命令。

优先使用已有的 `playwright-cli`。若缺少，可在项目内安装 `@playwright/cli` 开发依赖并通过 npm／npx 调用，保存 lockfile；避免无必要的全局安装。CLI 文档见 [Playwright CLI](https://playwright.dev/agent-cli/introduction)。

启动本地开发服务后，典型检查流程如下；端口与参数以实际环境为准：

```bash
playwright-cli --help
playwright-cli -s=alpha-v1 open http://127.0.0.1:5173 --headed
playwright-cli -s=alpha-v1 resize 1644 957
playwright-cli -s=alpha-v1 screenshot --filename=outputs/qa/home.png
```

创建输出目录后再保存文件。若使用项目内命令，则为上述调用添加相应的本地执行前缀。截图命令可参考 [官方截图说明](https://playwright.dev/agent-cli/commands/screenshots-pdf)。

获取快照后，用实际返回的元素引用操作热区。也可以通过 CLI 的代码执行能力使用稳定 locator 或内容区坐标移动鼠标，验证真实 hover 停留与离开行为。不要仅调用内部状态 setter 来替代导航验证。

### 开发检查能力

建议提供仅在开发／测试环境启用的检查接口，用于：

- 读取当前场景状态和转场进度；
- 固定随机 seed 与空闲时间；
- 暂停并定位启动／转场时间轴，捕获 0%、25%、50%、75%、100% 的画面；
- 导出帧间隔样本与渲染统计。

截图定位可以使用检查接口，交互验收仍必须通过真实指针事件完成。开发面板默认隐藏，正式画面不出现性能数字、状态名或技术说明。

### 必须检查的流程

| 编号 | 检查 | 通过条件 |
|---|---|---|
| V01 | 启动若干关键帧 | 双手渐进生成；大脑、科技树、输入框均未提前出现 |
| V02 | 主画面参考对齐 | 指尖、腕部、轮廓与留白有可复查的比较证据 |
| V03 | 右手 hover | 局部轻微反应；离开后平滑恢复；不破坏整体手形 |
| V04 | 短暂经过导航角落 | 未达到停留阈值时不导航 |
| V05 | 主画面到左上 | 相机与左手变形连续；大脑和输入框随运动引出 |
| V06 | 左上停留与输入 | 相机稳定，输入正常；鼠标离开原热区不自动退回 |
| V07 | 左上右下角返回 | 大脑逆向重组为左手，辅助手恢复，回到同一构图 |
| V08 | 主画面到右下及返回 | 粒子手与科技树连续转换，反方向 hover 正确返回 |
| V09 | 快速移动、重复 hover | 转场不重入、不叠加，不出现卡住或来回抖动 |
| V10 | 视口变化 | 在参考尺寸、常见 16:9 和 16:10 窗口下，指尖与核心轮廓不被裁掉，热区仍可操作 |
| V11 | 输入框可见范围 | 仅左上目的地存在可见且可聚焦的自然语言输入框 |
| V12 | 反复往返 | 至少 10 次往返后，构图不漂移，无明显资源持续累积 |
| V13 | 氛围开关 | 关闭时主流程完整；若实现开启模式，两种模式导航一致 |
| V14 | 离线与异常 | 打包素材无缺失；无未处理异常、shader 错误或不必要的外部请求 |
| V15 | 减少动态效果 | 能到达相同目的地并返回，界面交互保持可用 |

对导航、防重入、隐藏输入框和往返恢复建立少量有意义的 Playwright Test。使用状态／可见性条件等待，避免大量固定 sleep。运行方式以项目脚本为准，标准入口为 `npx playwright test`，参考 [测试 CLI 文档](https://playwright.dev/docs/test-cli)。

### 视觉证据

至少保存主画面、启动中段、左右转场中段、两个目的地、两个返回中段以及参考对齐图。录制一次“启动 → 左上 → 返回 → 右下 → 返回”的完整过程；如果录制不可用，提供有时间标记的连续截图。

Canvas 场景不能只凭 DOM snapshot 验收。必须实际查看截图与动态过程，检查解剖、穿插、粒子突变、透明层次、连线时序和内容闪现。

### 性能证据

在真实可用环境中，加载预热后分别记录主画面、目的地停留和连续转场的帧间隔。记录机器／系统、浏览器或桌面外壳版本、视口、DPR、质量档位与是否为有头运行。

区分浏览器帧间隔、渲染统计和真正的 GPU 测量；没有测量的数据不要填入报告。Headless 或软件渲染结果不能当作这台 Intel 笔记本的硬件加速性能结论。

## 13. 最终交付与完成标准

交付：

1. 可运行源码、依赖 lockfile、所需本地素材与复现脚本。
2. README：实际验证过的安装、浏览器预览、桌面开发、构建和测试命令，以及 Arch Linux 依赖说明。
3. `docs/VISUAL_V1.md`：当前视觉与交互规格。
4. 决策文档：与旧 IDEA 的差异、工程默认值、边框氛围粒子默认关闭、外壳选择及实测依据。
5. 素材来源与许可记录。
6. `outputs/qa/`：关键截图／录制、参考对齐证据、简短的浏览器与桌面验证报告。

完成报告必须区分“实现完成”“浏览器验证通过”“桌面验证通过”。不能把设计意图、占位手模型或尚未运行的测试写成完成事实。

本次工作的高优先级是：**参考图手形匹配、雕塑与几何构造美学、粒子手可读性、主变形和逆向返回、流畅的空间导航**。可选氛围效果和后续业务功能不应挤占这些工作。

直接推进已明确的工作。动画参数、代码拆分和常规依赖选择自行判断并记录；只有出现必须由用户决定的素材、预算或实质需求冲突时才提问。保持本地实现和可检查的交付，本任务不要求创建 GitHub release、推送远端或公开部署。

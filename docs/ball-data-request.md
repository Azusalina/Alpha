# 球需要什么数据(给 [back] 的请求,2026-10-03,D68)

球页面表示"模型对一个人的拟合"。设计见 `design/ball-design.md`。前端目前只显示固定的示例数据;
后端给出下面的字段后,前端只需在 `src/app/` 里加一个适配,不需要改球本身。

## 球要的形状

每个模型参数(13 个,与 `state` 返回的一致)一行,三个量:

| 字段 | 范围 | 含义 | 画成 |
| --- | --- | --- | --- |
| `fit` | 0..1 | 模型对这个参数拟合了多少。没有证据 = 0 | 波纹的活跃程度 |
| `peak` | 0..1 | 这个拟合有多集中:0 = 均匀分散在许多陈述上,1 = 由少数强烈陈述承担 | 尖刺的长短(< 0.2 不画) |
| `thin` | bool | 拟合建立在很少的证据上 | 尖刺画成空心 |

## 前端自己能推的(不需要后端)

`state` 已经给每个 (分区, 参数) 的 `{value, support, observed}`。前端可以拿 `support` 推一个单调饱和的 `fit`,
但 **`peak` 无法从 `state` 推出**:它需要知道支持这个参数的各条输入的贡献分布,而前端只有每条输入各自的 effects
(要全部读出来再算,代价高,且口径应由后端定)。

## 请求

1. 一个只读方法(例如 `fit_profile`,不需要参数,或可选 `partition?`),返回上表三个量,每个参数一行,
   并带 `model_epoch`,让前端知道它和哪一轮模型对应。
2. `peak` 的口径由后端定义并写进 `api.md`(例如:支持该参数的各输入贡献的集中度,基尼系数或前 k 条占比都可以);
   前端只当它是 0..1 的数,不是概率,也不解释它的算法。
3. `fit` 的口径同样由后端定义;前端不把它说成准确率或风险值。球不显示任何临床含义。
4. 没有证据的参数 `fit = 0` 且 `observed = false`;前端据此画静止表面。

## 不需要

不需要球专用的视觉字段(位置、颜色、长度):映射由前端负责。
